## Bug #1 — Submit closes drawer but no `POST /api/auth/users` observed
- After clicking "Tạo tài khoản", the drawer dismisses (suggesting `AddPanel.handleSubmit → onSave` returned truthy)
- Re-querying `GET /api/auth/users` returns 7 users — none of them is `qa_test_iter02`
- `read_network_requests` for the tab shows two GETs to `/api/auth/users` but no POST
- `AddPanel.handleSubmit` (frontend/src/features/users/components/UserForm.tsx:249) calls `onSave` then `onClose()` only if `ok` is truthy. So either:
  - `doCreate` (useUserMutations.ts:14) returned `true` (success path) — but `userClient.createUser` would have fired a POST
  - The POST happened but was suppressed from the in-tab network log (possible chrome-MCP race condition during the tab redirect described in Anomaly)
- Cannot reproduce cleanly because quan's role was demoted mid-test (see Anomaly below)

**Probable root cause (needs follow-up):** click → form sends POST → backend returns success (or 4xx) → role-change side effect (see Anomaly) triggers ProtectedRoute redirect to `/my-forwarder-trips`, which evicts the network log snapshot before the next read. Alternatively: the drawer's Drawer `useConfirmShortcuts({ isOpen, onConfirm })` and the explicit `onClick={handleSubmit}` could double-fire and trigger an unexpected branch.
