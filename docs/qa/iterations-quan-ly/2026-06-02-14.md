## M16.1 — `/trips` container search — BUG FOUND + PATCHED

Typed `ABCD1234567` into the search input on `/trips`.

**Network log captured a 500 error:**
```
GET /api/trips?limit=25&page=1&dateFrom=2026-06-01&dateTo=2026-06-30&search=ABCD1234567 → 500
"Failed query: select count(*) from \"trips\" where (… and (\"trips\".\"trip_code\" ILIKE $3 or \"trips\".\"id\"::text ILIKE $4 or \"customers\".\"name\" ILIKE $5 or \"trucks\".\"license_plate\" ILIKE $6 or \"routes\".\"name\" ILIKE $7 …))"
```

### BUG-QL-009 — count query references joined columns without joining

`backend/src/services/trip.service.ts:799-805` — when `filters.search` is set, the **count** query selects from `s.trips` ONLY (no joins) but the `countConditions` array includes `customers.name`, `trucks.license_plate`, `routes.name` ILIKE predicates. Postgres correctly rejects the SQL with "missing FROM-clause entry for table 'customers'". The list query (line 779) uses `TRIP_RELATION_JOINS` which does join those tables, so list-side worked fine.

A worse aspect for UX: the frontend swallows the 500 silently and shows "Không tìm thấy chuyến đi nào" — looks like a clean empty state but is actually a server error. Users searching by container would see "no results" with no indication of the underlying SQL failure.

### Patch

`backend/src/services/trip.service.ts`:
```ts
const [countRow] = filters.search
  ? await TRIP_RELATION_JOINS(db.select({ count: sql<number>`count(*)` }).from(s.trips))
      .where(and(...countConditions))
  : await db.select({ count: sql<number>`count(*)` })
      .from(s.trips)
      .where(and(...conditions));
```

The simplified count query now uses the same joins as the list query. The intent of the previous code was to skip the expensive container EXISTS subqueries for count — the patch preserves that (countConditions still drops the 2 EXISTS predicates, so count is approximate). The fix only addresses the missing JOIN, not the count-vs-list inconsistency. That's by design and documented in the existing comments at lines 764-766.

### Verification

After patch, re-tested:
```
GET /api/trips?limit=25&page=1&dateFrom=2026-06-01&dateTo=2026-06-30&search=ABCD1234567 → 200
  items: [{id:12, code:"TRP-202606-0009"}]
  total: 0  ← approximate-by-design; row still renders
```

UI: searching ABCD1234567 on `/trips` now shows 1 row (trip 12) with the green carrier mark, customer NITODA, ĐÃ KHÓA status pill. Footer reads "Hiển thị 1 trong 0 chuyến · Đã tải tất cả" — the "0" is the by-design approximation; the row is visible and correct. ✅ M16.1 passes.

> **Minor polish suggestion (not patched):** the "trong 0" wording when items exist is confusing. A future polish should either suppress the count when search is active, or extend `countConditions` to include the container EXISTS predicates accepting the perf cost (small data scale here makes the perf concern minor).
