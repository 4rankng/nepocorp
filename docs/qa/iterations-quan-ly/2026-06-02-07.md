## Setup recap

After iter 06: customer 1 ↔ supplier 1 linked both ways.

## M9 — Accountant creates offset

```
POST /api/finance/debt-offsets  (as anh)
{customerId:1, supplierId:1, offsetDate:"2026-06-02", note:"Đối trừ công nợ tháng 5 - M9 test"}
→ {id:1, amount:"3000000", approvalStatus:"PENDING"}
```

- M9.1 ✅ endpoint exists and accepts ACCOUNTANT.
- M9.2 ✅ Body intentionally has no `amount` field. Server computes `min(AR=11.8M, AP=3M) = 3M` (debtOffset.service.ts:62) — `DebtOffsetModal.tsx:23` shows the same `Math.min(arBalance, apBalance)` read-only.
- M9.3 ✅ Pre-approval balances unchanged:
  ```
  CUSTOMER 1: 11,800,000   (unchanged)
  VENDOR   1:  3,000,000   (unchanged)
  ```

## M10 — Manager approves

```
POST /api/finance/debt-offsets/1/approve  (as phung)
→ {id:1, approvalStatus:"APPROVED", ...}
```

Post-approval ledger entries (txn_id=1, ADJUSTMENT pair):
```
id 27 | ADJUSTMENT | CUSTOMER | 1 | credit=3,000,000 | balance=8,800,000  | "Đối trừ công nợ #1"
id 28 | ADJUSTMENT | VENDOR   | 1 | debit=3,000,000  | balance=        0  | "Đối trừ công nợ #1"
```

- M10.1 ✅ MANAGER approval action flips status to APPROVED.
- M10.2 ✅ AR balance: 11,800,000 → 8,800,000 (−3M). AP balance: 3,000,000 → 0 (−3M). Both reduced by exactly the offset amount.
- M10.3 ✅ Two ADJUSTMENT entries posted: customer-side CREDIT reduces AR, vendor-side DEBIT reduces AP. Matches guide wording exactly:
  > "Sổ kế toán của Khách hàng xuất hiện một dòng điều chỉnh ghi CÓ làm giảm công nợ phải thu. Sổ kế toán của Nhà cung cấp xuất hiện một dòng điều chỉnh làm giảm công nợ phải trả."

## Observations (NOT filed as bugs)

1. **Approval response is stale.** `approveDebtOffset` reloads the offset row at line 111 BEFORE stamping `approvedBy`/`approvedAt` (lines 158-161). DB row is correctly stamped (verified: `approved_by=3 phung, approved_at=2026-06-02 15:05`) but the API response shows nulls. UI refetches the list so this is invisible to users; minor service-layer ordering nit.
2. **Initial reject was a test-data pollution issue.** My iter-06 raw INSERT into `ledger` with wrong sign convention (balance=−3M instead of +3M for a credit posting on VENDOR) caused `createDebtOffset` to reject with "Không có số dư". Fixed by appending a compensating ADJUSTMENT credit entry (id 26, +6M to bring running balance to the correct +3M). The system's sign convention is correct: `ledger.service.ts:74-78` — VENDOR `newBalance = prev + credit − debit`, so AP-bearing entries are positive.
