# Iter 15 — Trip search × month-chip bug (M16 blind spot)

**Items:** M16 follow-up — trip-list search × month filter interaction
**Role:** MANAGER `phung`
**Date:** 2026-06-03
**Method:** Chrome MCP

## Bug

`/trips` with the month chip on **Tháng 6 / 2026**, searching `TRP-202605-0003`
(a May trip) returned the empty state "Không tìm thấy chuyến đi nào", even though
the trip exists and shows up in `/audit-logs` for recent fee activity. User intent
when typing a trip code is "find this trip regardless of when" — the silent month
filter made the trip look deleted.

## Root cause

- `frontend/src/pages/TripListPage.tsx` always sent `dateFrom` / `dateTo` (derived
  from the topbar month chip via `useSalaryPeriod`) to the list endpoint.
- `backend/src/services/trip.service.ts` `getTrips()` AND-combined those with the
  search predicate.
- Trip `TRP-202605-0003` has `departureDate` in May, so it was excluded by the
  June window.

## Fix

- Frontend: when `debouncedSearch` is non-empty, omit `dateFrom`/`dateTo` from
  the list query and the export call, and surface a green "Đang tìm trên tất cả
  tháng" hint pill next to the search input so the inactive month chip is
  self-explanatory. Status tabs + truck/customer pills still apply.
- Backend: same gating in `getTrips()` as a defense layer for non-UI callers.

## Verification

Logged in as MANAGER `phung`, opened `/trips` on Tháng 6 chip, typed
`TRP-202605-0003`. Result: 1 row — `TRP-202605-0003 · 31/05 · CÔNG TY CỔ PHẦN
NITODA · 15C-180.99 · Hải Phòng → Chè Ngọc Thanh, Phú Ninh, Phú Thọ · 20DC ·
SEGU3231738 · 147 L · 34,7 L/100km · HOÀN THÀNH`. Hint pill rendered. Footer:
"Hiển thị 1 trong 1 chuyến · Đã tải tất cả".

## Blind spot in prior QA

Iter 11 verified M16.2 (debt list container search) and iter 14 verified M16.1
(trip list container search). Both used **`ABCD1234567` → TRP-202606-0009** —
the matching trip happened to be in the same month as the active chip, so the
date-range × search AND-bug never surfaced. M16 was passed as "✅ end-to-end
through UI" without exercising the cross-month case.

### Recommended QA pattern going forward

When verifying any list-page search box that lives on a page with a month chip:

1. Confirm a hit exists when the search target is **inside** the active month
   (existing M16 coverage).
2. Switch the month chip away from the target trip's month and re-run the same
   search — must still return the same row, with a visible "all months" hint or
   equivalent affordance.
3. Clear the search — confirm the month filter snaps back into effect.

This applies to all list pages with a topbar month chip: `/trips`,
`/finance/expenses`, `/forwarder/expenses`, `/debt`, `/audit-logs`, etc.
