## Phase 1 — Lead QA report

### Bug 1 — Forwarder expense form is missing the **supplier (NCC)** and **container number** fields

**Surface:** `frontend/src/pages/ForwarderTripDetailPage.tsx` lines 41-52 (`expenseForm` state), 375-513 (form render block).

**Observed:** The inline expense form on the forwarder portal trip detail shows:
- ✅ Loại chi phí (`expenseType`) — 8 codes confirmed: LIFTING, LOWERING, WEIGHING, CUSTOMS, INFRASTRUCTURE, INSPECTION, INSPECTION_SVC, OTHER.
- ✅ Giá mua vào (`buyAmount`).
- ✅ Giá bán ra (`sellAmount`) — readonly for pass-through types, editable for markup types (CUSTOMS, INSPECTION_SVC). Markup gating implemented via `FORWARDER_EXPENSE_TYPE_DEFAULTS[type].defaultMarkup`.
- ✅ Hình thức chi (`settlementMethod`) — `FORWARDER_ADVANCE` / `COMPANY_DIRECT`.
- ✅ Số hóa đơn / Ngày hóa đơn (hidden for INFRASTRUCTURE — sensible).
- ✅ Số tờ khai (`declarationNumber`) — conditionally shown only when type=CUSTOMS, required client-side (line 139).
- ✅ Ghi chú (`note`).

**Missing — but specified in the plan and accepted by the backend:**
- ❌ **`supplierId` (NCC / Nhà cung cấp)** — required by D-A: `COMPANY_DIRECT` fees post `VENDOR_EXPENSE` AP against `supplierId`. Without this field, COMPANY_DIRECT-settled fees cannot be tied to a supplier, breaking AP attribution at lock.
- ❌ **`containerNumber`** — REVISED §2.2: "Số container là trung tâm truy xuất". Plan A1 adds an index on `trip_expenses.container_number`; B1 says create accepts `containerNumber`.

**Evidence — backend accepts both fields:**

`backend/src/services/forwarder.service.ts` (`createTripExpense` ~ lines 220-256):
```ts
data: {
  ...
  supplierId?: number | null;
  containerNumber?: string | null;
  ...
}
// inserts: supplierId: data.supplierId ?? null, containerNumber: data.containerNumber ?? null,
```

`backend/src/routes/forwarder.ts` (`POST /forwarder/me/expenses` ~ lines 66-85):
```ts
const parsed = tripExpenseSchema.safeParse(req.body);
...
supplierId: parsed.data.supplierId ?? null,
containerNumber: parsed.data.containerNumber ?? null,
```

Both fields flow through Zod (`tripExpenseSchema` in `shared/src/schemas/index.ts`) and persist into `trip_expenses` (schema columns confirmed: `supplier_id` FK → suppliers, `container_number` VARCHAR(20), index `trips_container_idx`).

**Why this is a real bug, not a UI nit:**
1. **Functional:** `COMPANY_DIRECT` settlement is supposed to post supplier AP; without `supplierId` the system has no supplier to credit. The forwarder is the only role who sees the fee buy-side at entry time, so the frontend gap is the constraint, not the backend.
2. **Audit/reporting:** Container-centric lookup (search/filter by container number) is broken for forwarder-entered fees if the field is never captured.
3. **Per the plan, intentional, not nice-to-have:** these are two of the seven fields F1.1 lists.

**Repro:**
1. Log in as `quan` (FORWARDER) → `/my-forwarder-trips`.
2. Open any trip with status `MỚI TẠO` (e.g., trip id 13 / TRP-202606-0010).
3. Click "+ Thêm" in the "Chi phí phát sinh" panel.
4. Observe the rendered form: no Nhà cung cấp/NCC select, no Số container input.

**Suggested fix:**
- Extend `expenseForm` state to include `supplierId: ''` and `containerNumber: ''`.
- Add two `FormGroup`s in row 2 (or new row 3): a supplier `<select>` (sourced from `useCatalogs().suppliers` — confirm catalog already exposes them, otherwise add) **shown only when `settlementMethod === 'COMPANY_DIRECT'`** (gated since FORWARDER_ADVANCE doesn't need supplier AP), and a plain `containerNumber` input (free-text — UPPERCASE the value on blur to match other container UIs).
- Wire both into the `createExpenseMut.mutate(...)` payload.
- Reset both in the `onSuccess` clear handler.

## Phase 2 — Patch report (Senior Eng)

**Scope:** add `supplierId` and `containerNumber` to the FORWARDER expense form, wire them through the mutation/client/route, and expose suppliers via a forwarder-scoped endpoint (forwarders are 403 on `/catalogs/bootstrap`).

**Files changed:**
- `backend/src/services/forwarder.service.ts` — added `listActiveSuppliersForForwarder()`.
- `backend/src/routes/forwarder.ts` — added `GET /forwarder/me/suppliers` (mounted under existing `casbinAuthz('forwarder')`).
- `frontend/src/api/forwarderClient.ts` — added `listSuppliers()`; extended `createExpense()` payload type with `supplierId` and `containerNumber`.
- `frontend/src/hooks/useForwarderQueries.ts` — extended `useCreateForwarderExpense` mutation type with the same fields.
- `frontend/src/pages/ForwarderTripDetailPage.tsx` — added `supplierId` and `containerNumber` to `expenseForm` state, render conditional Nhà cung cấp picker (only when `settlementMethod === 'COMPANY_DIRECT'`), always-render Số container input, validation error when COMPANY_DIRECT lacks a supplier, reset both in `onSuccess`, plumbing to the mutation payload, dedicated `useQuery` for forwarder suppliers (since FORWARDER 403s on the bootstrap catalog).

**Why a separate suppliers endpoint:** FORWARDER doesn't have `config:read`; mounting `/suppliers` under existing `forwarder` Casbin resource keeps blast radius minimal and avoids loosening the broader config policy.

**Notes:**
- `containerNumber` is uppercased on submit (`.toUpperCase()`) to match the convention used elsewhere for container codes.
- `useCatalogs.ts` was momentarily extended to include `suppliers`, then reverted — the actual fetch is via a dedicated forwarder query because bootstrap is not reachable for FORWARDER.
- Markup/pass-through behavior, the CUSTOMS conditional declaration field, the readonly sell amount for at-cost types, and the existing buy/invoice/note inputs are all unchanged.

**Build:** `npx tsc --noEmit` clean on both `frontend/` and `backend/`. Vite HMR + backend `tsx` watch already picked up the change.
