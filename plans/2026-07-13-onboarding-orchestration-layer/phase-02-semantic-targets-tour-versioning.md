# Phase 2: Semantic Tour Targets & Tour Versioning

## Overview

Two small, independent, purely-additive hardening changes to the tour catalog
and the target resolver, landing before Phase 3 consumes them:

1. **Tour versioning** — add a required `version: number` to the `Tour` interface
   and to all 3 existing tours. Version becomes part of the progress key in
   Phase 4 and the analytics payload in Phase 5.
2. **Semantic target resolver** — formalize a single `resolveTourTarget(targetId)`
   that looks up by **`[data-tour-id]` first, falling back to `[id]`**. Existing
   stable `id`s (`trip-new-submit`, `fuel-save-config-button`, …) keep working
   unchanged; `data-tour-id` becomes the convention for new/dynamic targets.

No runtime tour behavior changes in this phase — only the schema, the catalog
data, and the resolver function. Phase 3 swaps `agentHighlight.ts`'s raw
`getElementById` to use this resolver.

## Requirements

- **Functional**
  - `Tour.version: number` required; all 3 catalog entries bumped to `version: 1`.
  - `resolveTourTarget(id): HTMLElement | null` — selector precedence:
    `[data-tour-id="<id>"]` → `[id="<id>"]` → `null`.
  - `waitForTourTarget(id, { timeoutMs })` — polls `resolveTourTarget` until the
    element is mounted **and visible** (`offsetParent !== null`), as recommended
    by the brief §5. Default timeout 10 s.
  - Catalog integrity test extended to assert every tour has a positive integer
    `version`.
- **Non-functional**
  - No change to any existing `id` attribute on any page.
  - No new dependencies.

## Architecture

```
shared/src/tours/schema.ts           # add `version: number` to Tour
shared/src/tours/catalog.ts          # set version: 1 on all 3 tours
shared/src/tours/catalog.test.ts     # assert version present + positive

frontend/src/lib/tourTarget.ts       # resolveTourTarget + waitForTourTarget
frontend/src/lib/tourTarget.test.ts
```

**Why support both `data-tour-id` and `id` (decision D3):** the existing catalog
already targets stable DOM `id`s that are referenced elsewhere (e.g.
`#customerId` is used by tests and deep-link focus). Migrating them to
`data-tour-id` would be churn with no benefit and risk breaking `?focus=` deep
links. New targets — especially elements whose `id` is generated by a list
renderer — should use `data-tour-id` to stay decoupled from React's generated
ID space. The resolver makes both first-class.

**`waitForTourTarget` visibility check:** the brief §5 correctly notes that a
mounted-but-hidden element (e.g. inside a closed accordion) should not be
spotlighted. `offsetParent !== null` is the cheap, dependency-free visibility
probe (matches the brief's example). `position: fixed` elements report
`offsetParent === null` even when visible — a documented edge case handled by
treating a non-null `getBoundingClientRect()` width/height as a fallback signal.
Keep the implementation simple; do not pull in an `isVisible` library.

**Version semantics (for Phase 4):** `version` is author-bumped whenever a tour's
*step sequence or step IDs change in a breaking way*. Cosmetic text edits do
**not** require a bump. Phase 4's unique constraint
`(user_id, tour_id, tour_version)` means a bumped version starts a fresh
progress row rather than corrupting an in-flight one.

## Implementation Steps

1. Add `version: number` to the `Tour` interface in `schema.ts`; update the
   doc-comment to define the bump policy (breaking step-sequence change).
2. Set `version: 1` on `create-trip`, `lock-trip-and-payment`, `fuel-config`.
3. Extend `catalog.test.ts`: for each tour, assert `Number.isInteger(version) &&
   version >= 1`.
4. Implement `tourTarget.ts`:
   - `resolveTourTarget(id)`: `document.querySelector(\`[data-tour-id="${CSS.escape(id)}"]\`)`
     ?? `document.getElementById(id)`.
   - `waitForTourTarget(id, { timeoutMs = 10_000 })`: poll every 100 ms; return
     the element once `resolveTourTarget` is non-null and visible; throw/return
     null on timeout (see Step 5 decision).
5. Decide the timeout return contract: **return `null` on timeout** (do not
   throw) — Phase 3's caller handles null as "target missing" and renders the
   recovery UX. Throwing would force try/catch at every call site.
6. Write `tourTarget.test.ts` using jsdom: a target present via `data-tour-id`
   resolves; present via `id` resolves; absent returns null after timeout;
   hidden (`display:none`) keeps polling until timeout.

## Success Criteria

- [ ] `Tour.version` is required; removing it from a catalog entry fails `tsc`
      and the catalog test.
- [ ] `resolveTourTarget('trip-new-submit')` finds the existing element by `id`
      (no migration needed).
- [ ] `resolveTourTarget('some-dynamic-target')` finds an element stamped with
      `data-tour-id="some-dynamic-target"`.
- [ ] `waitForTourTarget` returns null (not throws) after the timeout when the
      target never mounts.
- [ ] `pnpm build` + shared/frontend tests green; catalog integrity test still
      passes with the new `version` assertions.

## Risk Assessment

- **Risk:** Making `version` required breaks any out-of-tree consumer of `Tour`.
  **Mitigation:** `Tour` is internal to this monorepo (grep confirms only
  `catalog.ts`, `TourControllerContext`, `tools/tours.ts` use it); all are
  updated in this phase.
- **Risk:** `CSS.escape` not available in very old browsers. **Mitigation:**
  target browsers already run React 19 + Vite modern build; `CSS.escape` is
  universally supported there. No polyfill.
