# Phase 4: Server-Side Onboarding Progress & Task Persistence

## Overview

Make the server the source of truth for onboarding state. Add two Drizzle tables
— `user_onboarding_progress` (per tour-version) and `user_onboarding_tasks`
(checklist items) — plus a small REST surface under `/api/onboarding`. The
existing `tourProgress.ts` localStorage layer becomes a **read-through cache +
offline fallback**: writes go to server (fire-and-forget with retry), reads
prefer server with localStorage fallback. This unblocks cross-device resume,
admin visibility, and Phase 6's checklists.

This directly fulfills the brief's §7 schema and the standing TODO in
`tourProgress.ts:1` ("a future server-side migration … can import it cleanly").

## Requirements

- **Functional**
  - Two tables per the brief §7 (column names snake_case to match repo convention):
    - `user_onboarding_progress`: `id`, `user_id`, `tour_id`, `tour_version`,
      `current_step_id`, `status`, `started_at`, `completed_at`, `skipped_at`,
      `updated_at`. Unique `(user_id, tour_id, tour_version)`.
    - `user_onboarding_tasks`: `user_id`, `task_id`, `status`, `completed_at`,
      `metadata` (JSONB). PK `(user_id, task_id)`.
  - REST endpoints (role-gated to office roles, audited):
    - `GET /api/onboarding/progress` — current user's progress rows.
    - `PUT /api/onboarding/progress/:tourId` — upsert step/status (debounced
      client-side; server does a single upsert).
    - `GET /api/onboarding/tasks` / `PUT /api/onboarding/tasks/:taskId` — checklist.
  - Frontend `onboardingClient` (React Query hooks) wraps these; `tourProgress.ts`
    becomes the cache layer that the client reads/writes through.
  - On tour start, the controller reconciles server ↔ localStorage: if server
    has a newer `updated_at` for the same `(tourId, version)`, prefer server.
- **Non-functional**
  - Step writes are **debounced** (e.g. 1.5 s) and batched — not one request per
    Next click.
  - Server write failures do **not** block the tour; the cache holds state and a
    retry flushes later.
  - New `status` values use **pgEnum** (`onboarding_status`): `in_progress`,
    `completed`, `skipped`. Task status reuses a second enum
    (`onboarding_task_status`): `pending`, `completed`, `dismissed`.
  - All routes pass through `casbinAuthz('onboarding')` + `requireRoles` for the
    office roles; mutations flow through `audit.ts`.

## Architecture

```
backend/src/db/schema.ts                       # 2 tables + 2 pgEnums
backend/src/migrations/<ts>_onboarding.sql     # generated by drizzle-kit
backend/src/services/onboarding.service.ts     # progress + task CRUD logic
backend/src/routes/onboarding.ts               # REST router
backend/src/index.ts                           # mount router w/ casbin + audit

shared/src/onboarding/tasks.ts                 # closed catalog of task IDs (for Phase 6)
frontend/src/api/onboardingClient.ts           # React Query wrappers
frontend/src/lib/tourProgress.ts               # → becomes cache layer (server source of truth)
frontend/src/context/TourControllerContext.tsx # write-through on step change
```

### Write-through flow

```
user clicks Next
   → TourControllerContext updates in-memory state + localStorage (instant)
   → debounced onboardingClient.upsertProgress(tourId, version, stepId, status)
       → on success: noop (cache already correct)
       → on failure: mark dirty; retry on next step change + a periodic flush
```

### Reconcile-on-start flow

```
start(tourId)
   → const server = await onboardingClient.getProgress(tourId, version)  // best-effort
   → const local  = getInProgressStep(tourId)
   → pick whichever has the newer updated_at; if server newer, overwrite local
   → if versions differ → Phase 2 bump policy: prompt "nội dung đã đổi, bắt đầu lại?"
```

### ER (sketch)

```
users 1───∗ user_onboarding_progress     (user_id FK, unique user+tour+version)
users 1───∗ user_onboarding_tasks        (user_id FK, pk user+task)
```

`tour_id`, `tour_version`, `current_step_id`, `task_id` are **plain strings**
(not FKs to a tours table) — the tour catalog is TypeScript, not a DB table
(matches the brief §7 and the catalog-as-code decision D6 / HLD §10.3).

## Implementation Steps

1. Define the two pgEnums + two tables in `db/schema.ts`; `pnpm db:generate`;
   inspect the generated SQL; `pnpm db:migrate` in dev.
2. Write `onboarding.service.ts` with the four functions; use
   `onConflictDoUpdate` targeting the unique constraints. All functions take
   `userId` from the JWT (never trust a body `user_id`).
3. Write `routes/onboarding.ts`; mount in `index.ts`; add casbin policies. Verify
   a DRIVER JWT is rejected (403) and a non-office role cannot reach the routes.
4. Add integration tests under `backend/src/tests/onboarding.integration.test.ts`:
   - upsert then GET returns the row;
   - second upsert for the same `(user, tour, version)` updates, not duplicates;
   - a bumped `tour_version` creates a new row (old preserved);
   - role gate rejects non-office roles;
   - audit row written on PUT (assert via the audit service / table).
5. Build `shared/src/onboarding/tasks.ts` type + export.
6. Build `frontend/src/api/onboardingClient.ts` (React Query hooks). Wire into
   `api/keys.ts` query-key convention.
7. Refactor `tourProgress.ts` to expose `getUpdatedAt`; keep the rest of its API
   stable so Phase 3's call sites don't change.
8. In `TourControllerContext`: on `start`, reconcile server-vs-local by
   `updated_at`; on each step change, debounced write-through. On version
   mismatch, surface the "nội dung đã đổi" prompt.
9. Manual QA in staging: start a tour on browser A, refresh on browser B →
   resume picks up from server state.

## Success Criteria

- [ ] `GET /api/onboarding/progress` returns the caller's rows only (no
      cross-user leak — assert with two users in the test).
- [ ] Step progression in the UI produces debounced server writes (verify via
      network panel + a direct DB row check).
- [ ] A server write failure does not freeze the tour; state stays in cache and
      retries.
- [ ] Cross-device resume works: progress saved on one browser resumes on another
      after a page load.
- [ ] A bumped `tour_version` starts a fresh progress row and prompts the user;
      the old row is preserved.
- [ ] `casbin` + `requireRoles` reject DRIVER/FORWARDER (403); audit row is
      written on every PUT.
- [ ] All backend + shared tests green; `pnpm build` clean.

## Risk Assessment

- **Risk:** Per-step server writes create load + perceived lag.
  **Mitigation:** 1.5 s debounce + batch; localStorage stays the immediate
  source for the UI; server writes are async fire-and-forget.
- **Risk:** Reconcile logic picks the wrong side on clock skew between client
  `Date.now()` and server `NOW()`.
  **Mitigation:** always compare using **server** `updated_at` (the server
  returns it on every upsert); never trust client wall-clock for the decision.
  localStorage's `updatedAt` is only a hint for offline mode.
- **Risk:** Adding casbin `onboarding` resource without policy rows → every
  request 403.
  **Mitigation:** step 3 adds the policy.csv rows explicitly; test asserts
  office roles pass.
- **Risk:** Existing localStorage progress for current users becomes stale vs an
  empty server on first load after deploy.
  **Mitigation:** reconcile treats "server has no row, local has row" as
  *local wins and pushes up* (one-time backfill), so no user loses progress.
